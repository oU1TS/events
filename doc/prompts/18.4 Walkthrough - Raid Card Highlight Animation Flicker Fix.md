# Walkthrough - Raid Card Highlight Animation Flicker Fix

We have resolved the highlight animation micro-stutter and mid-animation restart flicker that occurred when landing on direct raid card deep links (`#raid-<N>`).

---

## 🔍 Root Cause Analysis

### 1. False-Positive Database Re-Renders
During page load, `loadPastRaids()` renders the cards from `raids.json` and cached submissions, immediately starting the 3.5s breathing highlight pulse. Meanwhile, `syncApprovedSubmissionsFromDatabase()` queries Supabase in the background. In `applyApprovedSubmissionsToDataset()`, every approved submission unconditionally set `hasChanges = true` even if `pastRaidsData` already contained the exact same data. This caused `filterAndRenderRaids()` to execute ~250ms into the page load, clearing `raidsContainer.innerHTML = ''` and recreating all DOM cards mid-animation. When re-rendered, the highlight animation was aborted and restarted from frame 0, producing a noticeable flash/flicker.

### 2. Double Animation Reset in `scrollToRaid()`
If `scrollToRaid()` was scheduled while the card was already glowing, it removed `.highlighted`, forced a browser reflow (`void card.offsetWidth`), and re-added `.highlighted`, canceling the pulse and restarting it abruptly.

### 3. Redundant Force-Fresh Cache Reloads
In `initCacheAndNotifications()`, stale tracker evaluations triggered `loadPastRaids({ forceFresh: true })` without checking if the newly fetched JSON differed from active RAM data.

### 4. CSS Transition vs Keyframe Competition
`.raid-card` possessed a 0.3s CSS `transition` on `transform`, `border-color`, and `box-shadow`. When `@keyframes highlightPulse` animated those identical properties, the transition and animation engines competed on initial frames, causing subpixel paint jank.

---

## 🛠️ Changes Implemented

### 1. Hardware GPU Compositing & Transition Isolation ([`style.css`](style.css))
Updated `.raid-card.highlighted` to isolate the keyframe animation from CSS property transitions:
```css
.raid-card.highlighted {
    transition: none !important;
    animation: highlightPulse 3.5s cubic-bezier(0.22, 1, 0.36, 1) forwards;
    z-index: 10;
    border-color: var(--accent) !important;
    will-change: transform, box-shadow;
    backface-visibility: hidden;
    -webkit-backface-visibility: hidden;
}
```

### 2. Deep Equality Change Checks ([`app.js`](app.js))
In `applyApprovedSubmissionsToDataset()`, added stringified JSON equality comparisons:
```javascript
const existingJson = JSON.stringify(pastRaidsData[index]);
const merged = Object.assign({}, pastRaidsData[index], raidPayload);
if (JSON.stringify(merged) !== existingJson) {
    pastRaidsData[index] = merged;
    hasChanges = true;
}
```
If the database records are identical to current RAM/cache, `hasChanges` remains `false`, completely eliminating redundant DOM wipes.

### 3. Idempotent Pulse Protection in `scrollToRaid()` ([`app.js`](app.js))
Guarded `scrollToRaid()` so that if the card is already glowing and running its countdown timer, it preserves the active animation without resetting:
```javascript
// If this card is already highlighted and actively running its pulse, do not restart
if (card.classList.contains('highlighted') && activeHighlightTimeout) {
    return;
}
```

### 4. Fresh Fetch Deduplication ([`app.js`](app.js))
In `loadPastRaids()`, verified that incoming data actually differs before initiating re-renders:
```javascript
if (pastRaidsData && options.forceFresh && JSON.stringify(freshData) === JSON.stringify(pastRaidsData)) {
    return;
}
```

## ℹ️ Clarification on Browser Console Messages

The browser console logs you observed:
1. `Error with Permissions-Policy header: Unrecognized feature: 'attribution-reporting' | 'private-aggregation' | 'join-ad-interest-group' | 'run-ad-auction'`:
   - These are standard, harmless Chromium/Blink warnings resulting from Privacy Sandbox headers injected by external ad/analytics networks or host servers. They do not block JavaScript execution or affect layout/animations.
2. `GET https://cdn.onesignal.com/sdks/web/v16/OneSignalSDK.page.js net::ERR_BLOCKED_BY_CLIENT`:
   - This occurs because an ad-blocker or privacy extension (such as uBlock Origin, Brave Shields, or AdBlock) blocked the third-party OneSignal push SDK. The portal handles this gracefully with safe fallbacks.
